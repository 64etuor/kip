# Self-Improving RAG Quality Control Plane Design

**Status:** Approved
**Date:** 2026-08-06
**Decision:** Automate experiments and recommendations; require an operator to activate a candidate or apply a breaking ontology migration.

## Objective

KIP continuously evaluates version-pinned parser, embedding, reranker, and retrieval candidates on reviewed real-corpus cases. It may recommend a candidate, but it never silently changes production retrieval or the meaning contract. Versioned ontology releases are diffed, classified, and migrated through explicit manifests without rewriting approved assertions in place.

## Architecture

The existing ports, parser registry, evaluation runner, shadow embedding spaces, and atomic semantic activation remain the execution plane. A small quality control plane adds immutable experiment manifests, typed promotion policy, and ontology compatibility reports. The control plane stores files as reviewable evidence; PostgreSQL remains canonical for operational data and all search/vector/graph states remain rebuildable projections.

```text
reviewed failures + golden/challenge/canary cases
                         |
                         v
               experiment manifest
                         |
                         v
       baseline and candidate shadow execution
                         |
                         v
 retrieval + evidence + answer + safety scorecard
                         |
                         v
              recommendation artifact
                         |
             operator approval required
                         v
                 atomic activation
```

## Experiment contract

Each `kip.quality-experiment.v1` manifest identifies one baseline and one candidate. Components are limited to `parser`, `embedding`, `reranker`, and `retrieval`. Every component records its adapter, package or model identifier, immutable revision, and configuration. The manifest also pins the dataset, corpus fingerprint, code fingerprint, promotion policy, and required category coverage.

An experiment is reproducible only when all fingerprints and component revisions are present. A recommendation is invalid when its report was generated by different code, configuration, corpus, or dataset content.

Promotion gates are fail-closed:

- no failed cases or ACL leaks;
- no regression beyond the declared per-category floor;
- evidence locator, latest-version, and stale-warning metrics must be measured when required;
- latency and optional cost ceilings must pass;
- answer groundedness, citation correctness, completeness, and refusal behavior must pass when the candidate affects generated context or answers;
- parser candidates must preserve source hashes and locator coverage;
- activation remains an explicit operator command.

## Learning loop

Production queries are telemetry, not training truth. Only a reviewed failure may enter `golden`, `challenge`, or `canary` data. The review record contains the failure category, expected evidence, ACL principal, and source revision. Dataset evolution is append-only and produces a new fingerprint. This prevents silent feedback poisoning and benchmark drift.

## Parser and model candidates

Candidate libraries are adapters behind existing ports. A library is never imported by the domain or application layers.

- HWP/HWPX candidates compete on extraction success, text coverage, paragraph/table structure, locator fidelity, and retrieval impact. Parser disagreement creates a review item; it does not automatically merge text.
- PDF/DOCX/PPTX candidates may include a Docling adapter for layout, OCR, and table extraction. Existing native adapters remain the baseline. XLSX calculations continue to use exact original-range deep reads.
- Embedding candidates initially include pinned Qwen3 and BGE-M3 revisions.
- Reranker candidates initially include pinned Jina, BGE, and Qwen3 revisions.
- Dense, sparse, multi-vector, and lexical retrieval are separately attributable experiment components so an improvement can be traced to one change.

Heavy optional libraries are installed as extras or served behind HTTP adapters. The baseline installation stays lightweight and offline-capable.

## Ontology release and migration contract

An ontology release has a semantic version and a complete normalized catalog. `ontology diff` compares two release roots and classifies each change:

- `compatible`: additions and description-only changes that preserve existing meaning;
- `review_required`: risk, extraction, review-policy, or widening changes;
- `breaking`: removals, renames, domain/range narrowing, parent changes, and policy weakening.

A breaking release must provide `kip.ontology-migration.v1`. Supported operations are `rename`, `deprecate`, `replace`, `split`, and `merge`. Each operation identifies source and target symbols and whether assertion-level human review is required. The validator rejects uncovered breaking changes and migrations whose source or target symbols do not exist in the appropriate release.

Migration never mutates an approved assertion in place. It creates candidates under the target ontology version, preserves evidence and provenance, queues required reviews, and activates only after validation. The previous ontology version and its assertions remain readable for rollback and audit.

## CLI surfaces

- `kip quality validate-manifest --manifest ...`
- `kip quality recommend --manifest ... --report ...`
- `kip ontology validate --root ...`
- `kip ontology diff --before ... --after ... [--migration ...]`

All commands use the existing versioned JSON envelope. Recommendation does not activate anything. Existing `projection activate` remains the explicit semantic activation surface.

## Failure handling and security

Malformed manifests and ontology releases fail before execution. Candidate failures are recorded per case and cannot replace an active parser extraction or projection. Corpus paths and document contents are never written into public reports. ACL filters execute inside each retrieval candidate, and forbidden-document counts are a hard gate. Source files remain read-only.

## Verification

The implementation is accepted only when unit tests cover manifest parsing and compatibility classification, CLI tests cover success and rejection envelopes, current ontology validates, a breaking fixture fails without a migration and passes with one, a recommendation cannot activate a projection, real canary evaluation produces fingerprinted artifacts, and `./scripts/verify.sh` passes.
